# Dropcheck 2.0 interactive Shell: decisions and tasks

Status: planning and implementation record, 2026-11-03. The original observations/checklist below describe the planning baseline, not an automatic assertion about the modified code. See the implementation revision immediately below and [the actual command/extension contract](commands.md). This document is intended to be usable without the conversation that produced it. In this document, **decided** means an explicit product requirement; **observed** means verified in the existing code or cited documentation; **proposed** means a design or command candidate requiring implementation review; **open** means it must not be silently guessed.

## Implementation revision (2026-11-03)

The user explicitly approved implementation, speed priority, and these resolutions of the original open decisions: implement networks/default/explicit-ID/permissions and link `family all`; omit events/`tcping`/cosmetic configuration mode; use session-only default credentials and remove Android's old plaintext value; portable bounded regex, blank-inclusive logical-line counts, and safe presentation JSON on both Shells with no text-filter combination. No device install, live probe or Wi-Fi mutation is authorized by that implementation request.

The code now contains the generated portable inventory, both typed parser adapters, contextual help/completion/history, session defaults, both pipeline engines, new read-only protocol/execution operations and targeted display fixes. Exact APIs, semantics, extension steps and remaining display/device acceptance boundaries are documented in `commands.md`. Test/build results are recorded at the end of this document when verification finishes. **The unchecked original acceptance items are not certified complete merely because these paths are implemented**; in particular, exhaustive per-field coverage/deduplication and real-device readability remain separate acceptance work.

## Objective and boundaries (decided)

- The first Dropcheck 2.0 task is to finish **both interactive Shells**: the PC Controller Shell and the Shell inside the Android app. Give network engineers familiar, predictable operation while making future changes straightforward to maintain.
- The PC **one-shot CLI is out of scope**. Do not mistake shared Go parser or renderer code for permission to redesign its user interface. If shared internals change, protect the one-shot CLI's existing behavior with tests. The Controller TUI and harness are not additional Shell UIs to redesign either.
- Common commands must have the same names, validation, help, outcomes, and output meaning on PC and Android. PC-only host capabilities (ADB, connected-device listing/selection and multi-device broadcast) must be clearly identified, not simulated on Android. Android may provide small-screen input shortcuts without changing the canonical commands.
- Do not ship a staged compatibility migration for the 2.0 Shell. Design the replacement as a single coherent cutover; remove superseded Shell paths and dead code. Internal development may be sequenced, but a released half-old/half-new Shell is not the goal. This does **not** authorize unrelated protocol or one-shot CLI breakage.
- `show` must present **all safely obtainable information relevant to the requested subject**, without repeating the same fact from the same subject/observation. Do not collapse observations from different sources or times: Android's measurement and a PC/ADB supplement are different evidence even if their values happen to agree. Distinguish unavailable, absent, false, stale, failed, and redacted rather than inventing values.
- Recognize PC terminal width and Android's actual content width. Preserve full safe values; arrange them appropriately for narrow, medium, and wide displays. Never equate a narrow screen with permission to omit information or force an unnecessarily compact view on a wide one.
- Support `|` with `begin`, `match`, and other explicitly specified filters in **both interactive Shells**. Contextual `?` must work without Enter; completion, editing, history, and feedback are part of the Shell task, not polish postponed to another release.
- New command development must have a documented, mechanical change path. Maintainability is a first-class acceptance criterion, not merely two Shells that happen to look alike. No speculative universal factory or plugin framework is required.

## Existing system: observations, not specifications

- PC: `controller/internal/command/grammar.go` declares paths/options and builds operations; `controller/internal/shell/parser.go` splits the line and classifies commands; `controller/internal/shell/help.go` supplies help/completion; `controller/internal/app/repl.go` owns readline, target state and execution. Android: `agent/src/main/java/io/dropcheck/agent/AgentInteractiveShell.kt` separately declares syntax, validation and help; `MainActivity.kt` owns input and transcript; `AgentShellAdapter.kt` bridges to `CommandExecutor.kt` and local renderers. These are **two implementations**, not a cross-language shared grammar.
- Existing common agent operations include Wi-Fi status/diagnostics/capabilities/scan/scan detail/connect/disconnect/forget/wait/assert/monitor/reconnect/cycle; IP status; ping, traceroute, path MTU, global IP, DNS, HTTP and download. `show wifi eht` is a composite command. The Android registry (`AgentCommandRegistry.kt`), PC grammar, protocol (`proto/dropcheck/v1/control.proto`) and existing shared E2E cases are useful starting points, but do not form one complete source of truth for interactive UX.
- PC has a readline `?` key handler and Tab completion; the Android EditText submits on IME action and treats `?` as a command **after** submission. PC help currently trims input in a way that loses the distinction between a question mark attached to a partial word and one after whitespace (`shell/help.go`). Help, parser, completer, and literal/quote handling must agree; do not interpret a `?` inside a literal as help.
- PC's `controller/internal/pipeline/pipeline.go` already accepts `match`, `except`, `count`, `display json`, `display set`, `no-more`; it lacks `begin`. `display set` has no corresponding set-command renderer and `no-more` does not control a pager. Android rejects a pipe. PC currently filters **rendered/wrapped** output; a terminal width change can change matches and counts. `app/repl.go` also appends some findings/supplements after the main renderer's width pass.
- `render/presentation.go` repeats SSID/BSSID and other connection facts between Wi-Fi overview and `Connection` detail, and repeats scan BSSID between a table and subsequent per-AP records. `render/render.go` emits latency in both a heading and a separate `Latency` line. The diagnostic bundle renders constituent status and network/IP sections; do not deduplicate across different observations without checking identity and provenance.
- Android `AgentWifiScanRenderer.presentation()` receives `brief` but does not use it. The basic scan and subsequent detail table repeat BSSID. PC's EHT nearby-AP table in `render/render_wifi_mlo.go` limits SSID to 14 columns even on a wide terminal. PC gets TTY width in `app/render_bridge.go`; Android measures actual View content width and can reflow (`MainActivity.kt`, `AgentBlockPresentation.kt`). Android display has a 96-row/240-line budget and preserves full safe values through a separate inspect/copy path; do not describe that as complete on-screen visibility.
- `NetworkRepository.wifiDiagnostics()` collects all Android Networks and calls `ipStatus(network)` for each, **but** also collects Wi-Fi status, capabilities and scan. `show ip status` selects a Wi-Fi Network rather than serving as a general default-Network inspection. A light network-list operation is preferable to invoking diagnostics merely to display networks.
- PC target selection can pin a selected agent and deliberately broadcast; Android Shell targets self. Android `set default passphrase` persists a value in ordinary `SharedPreferences` (`AgentShellUse.kt`); treat storage, logging, copy, errors, and history as security boundaries, not just UI issues. Keep Device Owner requirements for mutating Wi-Fi operations distinct from read-only probes.
- Existing tests cover parser cases, a shared E2E command fixture, Go rendering width matrices, Android unit tests, and synthetic Android instrumentation. They do **not** establish complete real-device readability, every field's coverage, or both interactive front ends' equivalence.

## Functional work to complete

All boxes below are **tasks**, not claims that the behavior already exists. Where a precise choice is not yet settled, record it under Open decisions instead of inventing it.

### 1. Interaction and command language

- [ ] Specify an operator-facing grammar for the common operational commands, options, positionals, aliases, unambiguous abbreviations, quoted strings, escapes, literal `|`/`?`, invalid/incomplete input, and help at each cursor position. Retain canonical spellings across both Shells.
- [ ] Implement no-Enter contextual `?` for the empty line, partial keyword (`sho?`), next token (`show ?`), argument/value, and filter (`| ?`). Do not dispatch a device operation or destroy the edited line; respect cursor position, IME composition, accessibility and hardware keyboards. Provide an Android touch/IME affordance where a physical `?` or Tab is inconvenient.
- [ ] Make Tab/completion, candidate descriptions, ambiguity diagnostics, accepted grammar and help derive from the same command contract. Never complete secret values into history or echo a supplied credential. Keep PC line-editing conventions and add equivalent Android affordances without treating a phone screen as a terminal emulator.
- [ ] Define history, recall, cancellation, progress, prompts, selection visibility and clear error/status messages. A displayed transcript is **not** command-history recall. Do not retain credential-bearing input. Do not present `#` as proof of privilege.
- [ ] Inventory commands across both Shells. Publish portable commands on both; explicitly label PC-only ADB, device selection and broadcast. Do not add an Android stub to the normal help merely to return "unsupported" after parsing.

### 2. Executable operations and configuration

- [ ] Prioritize read-only `show networks`, `show network default`, `show network <id>`, and `show permissions` across the Shells. A network list should obtain only necessary data; show transports, active/default identity, ID and observation state. A stale explicit ID must fail, never silently select another Network.
- [ ] Assess `check link ... family all` parity with the PC, including correct separate IPv4/IPv6 findings. Add `show wifi events last <count>` only after deciding safe event selection, redaction, retention and bounds. Do not claim that saved Wi-Fi inventory, Wi-Fi radio toggling, or fresh location data is available when platform capabilities are not established.
- [ ] Specify operation categories: read-only snapshots, active network probes, Wi-Fi mutations, and durable settings. State target and side effects before executing risky operations; prohibit accidental broadcast or silent fallback. Preserve permission/Device Owner checks and cancellation/timeout semantics.
- [ ] Decide whether any **real** persistent, non-secret settings justify a configuration hierarchy. If so, implement an honest target-scoped read/edit/validate/compare/apply/discard lifecycle and exit behavior; never stage actions that already happened. Decide separately whether a default Wi-Fi passphrase should be persistently stored at all and how to protect it. Until such a design exists, remove false configuration promises rather than adding a cosmetic mode.

### 3. `show`, width and output contracts

- [ ] Create a per-command field inventory for status, IP, scan/scan detail, EHT/MLO, capabilities, diagnostics, probe results and local results. For every safe obtainable field record its subject, source/time, unit, availability and default/detail placement. Handle unknown/new enum values without silently dropping them. Define which fields are intentionally redacted or out of scope.
- [ ] Present each fact once per subject/observation. Put key identity and verdicts in the overview, incremental evidence in `detail`; do not repeat entire overviews in detail. Preserve different source/time observations as separately labelled facts. A summary may aggregate counts, but must not mislabel an aggregate as a second measurement.
- [ ] Correct Android `scan brief` and ensure `brief` (requested reduction in depth) is distinct from automatic narrow-screen reflow. Define how a user reaches all safe values when an Android display budget is exceeded; display a clear count/continuation indicator, not silent clipping. Do not use an arbitrary short SSID cap at 120 columns.
- [ ] Normalize safe typed facts **before** layout. Apply PC terminal columns and Android measured pixels to tables, field wrapping and complete output (including error, source and findings), not just the primary scan section. Narrow = legible lossless records; medium = fitting tables; wide = useful columns without gratuitous whitespace or abbreviation. Unknown PC width/non-TTY must retain safe data.
- [ ] Keep source, age, partial acquisition, stale cached-scan status and permission limits visible. Do not claim an atomic snapshot when diagnostics is a bundle of independently acquired values. Do not present null/empty/default proto scalars as measured facts without observation metadata.

### 4. Output pipelines

- [ ] Support `| begin <pattern>` (include first matching **logical** line and all following logical lines; no match = no output), `| match <pattern>`, `| except <pattern>`, and `| count` on both interactive Shells. Define order as written, quoting/literal pipes, zero-match behavior and blank-line counting. Filter **before** width reflow so identical facts match at all widths.
- [ ] Choose a documented portable pattern syntax and bounded execution semantics for Go and Android; do not assume Go `regexp` and Kotlin/Java regexes accept identical expressions or have identical worst-case behavior. Validate an entire pipeline before dispatch; fail visibly on bad patterns, empty stages and unsupported combinations.
- [ ] Make command status independent of filtered text: zero displayed lines do not turn an unsuccessful acquisition into success. Decide explicit text-vs-structured-output semantics. In particular, reject line filters that would corrupt `display json`; preserve the structured output contract if JSON is supported on Android.
- [ ] Remove `display set` and `no-more` from help and parsing unless a real set-format renderer and pager are explicitly designed and implemented. Do not retain advertised no-ops for compatibility.

## Implementation and long-term maintenance work

The target is a *mechanical extension path*, not a promise that adding a new network operation can be accomplished by editing one file. Protocol, device execution, platform-specific UI and security boundaries remain distinct for good reasons.

- [ ] Establish **one authoritative portable command contract** describing canonical name, arguments, validation rules, operation kind, supported targets/platforms, side effects, help and completion metadata. Keep PC-only Shell commands in an explicit extension. Determine whether the smallest viable shared source is declarative data plus generated Go/Kotlin bindings, or a maintained contract plus conformance tests; do not add a generator or abstract factory without eliminating real duplication. Prohibit parallel handwritten inventories that drift.
- [ ] Give lexing/partial parsing a stable representation with token spans, quotes, cursor position and trailing whitespace. Use that representation for execution, `?`, completion and pipelines instead of independently splitting/trim-parsing the same line in each feature.
- [ ] Separate immutable command intent (typed request, selected/pinned target, effect class, presentation/pipe options) from per-UI input, runtime execution, output facts and layout. Prefer one explicit execution path per platform to hidden fallbacks, command-text inference or giant duplicated switch chains.
- [ ] Build a typed, provenance-aware presentation model for fields, sections, rows and failures. PC/Android can have separate final layout engines; their *field selection and meaning* must pass common contract fixtures. Keep validation and error normalization at shared boundaries. No string scraping of rendered text to determine success.
- [ ] Make safety part of extension registration: exhaustive handler/result checks, typed presence, explicit capabilities, target pinning, timeout/cancel cleanup, credential redaction before filtering/history/copy/logging, and fail-closed behavior for mismatched or missing results. Review ordinary `SharedPreferences` use for passphrases.
- [ ] Delete old or shadow paths in the cutover: duplicate registries/aliases/help lists, unused unsupported command placeholders, obsolete bridges if they add no boundary, unimplemented output-format/pager stages and dead render paths. **Check callers first**: PC one-shot CLI, harness and RPC clients may share types and cannot be casually removed just because interactive Shell code was replaced.
- [ ] Keep a short extension guide with a fixed change checklist and examples. For a hypothetical **future** `tcping`, the expected steps are: define behavior/side effects and input/result contract; add protocol fields only if the existing typed contract cannot express the result; implement bounded device execution; connect the common command declaration and the PC/Android adapters; supply safe facts/layout; add shared syntax/outcome/output tests and platform execution checks. This is an example of *mechanical work*, **not** approval to implement `tcping` now. Require new commands to register without editing multiple unrelated help/completion/alias tables.
- [ ] Have tests or build checks fail on missing handler, missing result mapping, help/grammar drift, unhandled platform applicability, or uncovered safe display fields. Avoid generic interfaces with a single implementation, reflective discovery, a runtime plugin system, or a second configuration language unless they demonstrably reduce real change cost.

## Acceptance checks for the 2.0 Shell cutover

- [ ] A command/option/capability matrix identifies common, PC-only and Android-only behavior, side effects and permissions. A common input yields equivalent typed intent, validation, results and interpretation on both Shells; differences are intentional and documented. Keep the PC one-shot CLI regression suite passing.
- [ ] Input matrix: empty line; `?`, `sho?`, `show ?`, argument help and `| ?`; Tab/touch completion; quoted whitespace, literal `?`/`|`, escapes, Unicode, partial/ambiguous commands, cursor edits, IME composition, and secret input. Help and completion must not execute network work.
- [ ] Output fixture matrix: each result payload and safe field, absent/unknown/false/redacted values, fresh/cached/failed acquisitions, status/detail/brief, multi-source diagnostics, ADB supplements, and multi-agent output. No duplicated fact within one observation; no dropped fact merely because width shrank. Check PC 24/40/80/120 columns and non-TTY, plus Android measured narrow/wide and rotation/IME in actual Views.
- [ ] Pipeline matrix: quoted literal pipe, `begin`/`match`/`except`/`count` composition, no match, invalid pattern, no-op removal, status/error preservation, JSON safety, and identical logical results regardless of screen width. Preserve safe full-value inspection when Android truncates the *visible* transcript for resource limits.
- [ ] Execution matrix: disconnected/reconnected PC target, deliberate versus accidental broadcast, self versus default/explicit Android Network, stale IDs, permission denial, Device Owner checks, timeout/cancel/partial response and secret handling. Never substitute a new target or success for failure.
- [ ] Add one hypothetical command through the documented extension path in tests or review to demonstrate a predictable, bounded edit list. Verify stale implementation is removed rather than hidden behind adapters. Run repository-native Go/Android tests, linters and proportionate device/instrumentation checks; document environmental limits if live-device verification is unavailable.

## Open decisions; do not silently assume an answer

1. Final command spelling, scope and data/permission contracts for `show networks`, network-by-ID, permissions, `family all`, and any event view. These are **proposals**, not approved exact syntax or promised Android APIs.
2. Whether 2.0 has any durable configuration surface at all; if yes, its ownership, atomicity, conflict handling and security. Vendor config-session semantics do not transfer to immediate Wi-Fi actions.
3. Portable regex subset, blank-line treatment in `count`, structured/JSON output availability on Android, and whether additional vendor filter aliases are worth maintaining. `begin` and `match` themselves are required.
4. Exact declarative command source, generation versus shared conformance fixtures, target folder layout, and how to isolate the one-shot CLI while removing obsolete interactive Shell code. Select the smallest implementation after tracing existing callers.
5. Human readability of live outputs on authorized Android devices and PC terminals. Synthetic width tests prove fit/retention properties, not real-world readability.
